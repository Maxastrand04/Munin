# ADR-0008: Phrase boosting runs Klang's vendored code through one module

**Decision:** Klang's phrase boosting code, `pianissimo_onnx.py`, `phrase_boost.py` and `tokenizer.model`, MUST be vendored at a pinned revision of `KlangAI/pianissimo-sv-onnx` under `src/munin/core/_vendor/klang/` with its CC BY 4.0 attribution, MUST be imported only by `src/munin/core/boosting.py`, MUST NOT be downloaded at runtime, and MUST boost only models that share its one `tokenizer.model`.

**Reason:** onnx-asr has no phrase boosting, and Klang ships it as loose files on Hugging Face, not as a package. Their README fetches the files with `huggingface_hub.snapshot_download` at runtime and imports them. That lost for three reasons. A module fetching with the hub and calling Klang's helper wraps two dependencies, which PCR-0004 forbids. The program would run code downloaded from the internet. And a change Klang makes upstream would reach users without anyone reviewing it. Vendoring costs about 6 KB of code and a 360 KB tokenizer, and turns each upstream change into a reviewed diff. The one tokenizer serves English too because Klang fine-tuned Pianissimo from Parakeet TDT 0.6B v3 and kept its tokenizer: the vendored file is byte for byte the one in NVIDIA's v3 checkpoint, and walks all 8,192 tokens against both repos' `vocab.txt` with no mismatch ([research report](../research/english-lecture-model.md)). A second vendored tokenizer chosen per model lost, since no model Munin loads needs one.

**Consequence:** `boosting.py` is the one module that imports the vendored helper. `model.py` hands it the loaded onnx-asr model, Pianissimo or Parakeet v3, and never imports the helper itself. `sentencepiece` is a project dependency because the helper needs it. The helper replaces a private onnx-asr method, `_decoding`, so `onnx-asr` stays pinned below 0.13, and raising that pin means re-vendoring from Klang or checking that boosting still decodes. Lint skips `_vendor/`, so the vendored files stay as Klang ships them and a re-vendor never turns the lint check red. English boosting relies on Parakeet v3 sharing this tokenizer, so moving English to another model, Parakeet v2 or English Pianissimo included, means checking its tokenizer against the vendored one first, and vendoring a second one with a per-model choice in `boosting.py` if they differ. A tokenizer that differs silently steers terms toward the wrong tokens, or raises `IndexError` on a smaller vocabulary. A `snapshot_download` of `*.py` files, a lint fix inside `_vendor/`, an import of the helper outside `boosting.py`, or boosting a model whose tokenizer nobody checked, breaks this record.

**Scope:** `src/munin/core/boosting.py`; `src/munin/core/_vendor/klang/`; `src/munin/core/model.py`, `load_recognizer`

**Date:** 2026-11-09
